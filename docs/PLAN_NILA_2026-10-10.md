# Dédale : plan issu de la session Nila du 10 octobre 2026

Ce document rassemble le cadrage achevé dans la session Nila avec Guilhem et Paul. Il sert de référence pour le dépôt et pour le travail partagé. Il restitue les décisions prises, puis les propositions que Nila avait laissées à valider avant de coder. Les échanges privés et les vocaux ne sont pas reproduits ici.

## 1. La direction retenue

Dédale est le rempart entre l'extérieur et les deux acteurs qui, dans l'entreprise, lisent et agissent : **les salariés et les agents IA**. Un pare-feu protège les tuyaux ; Dédale protège ceux qui décident d'ouvrir.

Pour ouvrir le pitch sur un fait mesuré : le [benchmark 2025 de KnowBe4](https://www.knowbe4.com/resources/reports/2025-phishing-by-industry-benchmarking-report) donne **33,1 % de personnes susceptibles d'interagir avec une simulation de phishing avant formation**, sur 67,7 millions de tests dans 62 400 organisations. Ce chiffre ne mesure pas Dédale et ne décrit pas le résultat après formation. Selon les retours des mentors KPMG rapportés pendant la session, cette entrée par le phishing salarié rend le problème immédiatement lisible ; la démonstration d'un agent attaqué puis défendu apporte ensuite la preuve technique attendue.

Un salarié peut suivre un mail de phishing ; un agent peut suivre une consigne cachée dans un document, un mail ou la description d'un outil. Le produit doit montrer ces deux chemins dans une même console SOC, avec une chaîne de faits lisible et une décision humaine explicite.

Le fil commun est : **signal → geste ou appel tenté → avertissement ou retenue → choix humain → conséquence journalisée → export**. La boîte noire conserve le contexte, la consigne suspecte, l'action demandée et ce qui s'est réellement passé. Un export SIEM et un brouillon NIS2 partent des faits observés ; le brouillon n'est ni une qualification juridique ni une notification envoyée automatiquement.

La démonstration doit ouvrir sur un geste salarié compréhensible immédiatement, puis montrer une attaque technique sur un agent interne, en direct. Le second parcours est la preuve centrale pour un jury technique : injection de prompt, outil MCP empoisonné, tentative de sortie de données ou appel hors droits. Le récit commun évite de présenter deux produits séparés.

## 2. Ce qui a changé pendant le cadrage

Le point de départ associait des leurres externes, des canaris internes et une boîte noire pour agents. Guilhem a ensuite choisi de concentrer la démo sur la protection des **agents internes**, avec le mail comme première surface. Les leurres qui attrapent des agents attaquants sur un site ou une API restent une piste distincte.

La discussion avec Paul a ajouté le salarié au cœur du produit : le phishing donne un point d'entrée évident au public, tandis que le scénario d'agent apporte la preuve technique. Le volet physique, les appels, les chatbots publics, les échanges entre agents et la mémoire de long terme sont sortis du périmètre de la démo. Du code exploratoire peut encore exister dans le dépôt ; sa présence ne signifie pas que ces fonctions sont prêtes.

## 3. Parcours à présenter

### Salarié

1. Camille reçoit un mail ou ouvre un lien trompeur dans un environnement fictif.
2. Le simulateur montre le geste risqué et un avertissement avant l'action.
3. Camille choisit **annuler** ou **continuer**. Annuler évite le geste simulé ; continuer produit un incident traçable.
4. La console montre le signal, le geste, l'avertissement, le choix et sa conséquence. L'analyste peut clore ou ignorer le dossier. Il ne coupe pas le poste du salarié.

Le phishing est la scène d'ouverture. Le secret collé, le mail envoyé au mauvais destinataire et l'upload vers une IA externe illustrent d'autres gestes déjà prévus par le simulateur. Deux scènes supplémentaires ont été proposées, sans validation explicite dans Nila : une fausse facture ou demande de virement usurpée, puis une demande MFA approuvée sans compréhension.

### Agent interne

1. Un agent fictif reçoit une tâche légitime et lit un contenu non fiable : mail, document ou description d'outil MCP.
2. Une instruction piégée tente de modifier son objectif, d'obtenir un secret, d'exfiltrer un rapport ou d'utiliser un outil hors de ses droits.
3. La passerelle retient l'appel à risque, relève le canari ou le dépassement de droits et ouvre un incident. La boîte noire reconstruit la chaîne **source → instruction → intention → appel d'outil → décision → résultat**.
4. L'analyste voit la preuve dans la console et choisit **couper** ou **reprendre** quand le scénario le permet. Couper suspend la session et révoque son jeton ; reprendre libère uniquement l'appel retenu. Une opération interdite par les droits reste bloquée même si l'agent la demande.
5. Les événements et exports décrivent le résultat réel. Une tentative n'est pas présentée comme une fuite réussie.

Pour la réalisation dans ce dépôt, le parcours reste reproductible hors ligne avec un agent scripté. Une version pilotée par un modèle peut servir à montrer une variation, mais la démo du jury ne doit pas dépendre d'une disponibilité cloud ou d'une réponse aléatoire.

## 4. Architecture visée

| Élément | Rôle dans la démo | Cible produit après la démo |
| --- | --- | --- |
| Poste salarié | Simulateur de gestes et d'avertissements | Application discrète sur le poste, intégrée aux surfaces réellement utilisées |
| Agent interne | Agent fictif et outils locaux, derrière une passerelle | Passerelle pour les agents et leurs appels d'outils, avec droits minimaux |
| Collecteur | Reçoit événements, sessions et incidents | Service déployé dans l'environnement de l'entreprise |
| Boîte noire | Conserve les phases et décisions vérifiables | Piste d'audit exploitable par la SOC |
| Console | Vue commune salariés/agents, décision et mesures | Tableau de bord opérationnel pour les analystes |
| Sorties | ECS, règles Sigma et brouillon NIS2 | Intégration SIEM et processus réglementaire contrôlé par l'entreprise |

L'application native de poste, la surveillance réelle du Mac, les connexions Outlook/Gmail et l'installation sur site décrivent **la cible produit**. Le prototype actuel utilise des gestes salariés simulés, un agent interne fictif et un backend local. Le pitch et la landing doivent garder cette distinction visible.

## 5. Mesure et preuve

La démo doit rendre visibles le signal d'entrée, l'action retenue ou laissée passer, la décision, le temps écoulé et l'état final. Le banc d'attaque doit produire des campagnes identifiables et un rapport limité aux sessions de la campagne mesurée : détection, faux positifs, faux négatifs, sessions absentes ou non classées, avec leurs dénominateurs. Les mesures globales du backend doivent être nommées comme telles. Aucun taux obtenu sur trafic synthétique ne prédit une performance en production.

Le dépôt doit montrer les limites au même endroit que les résultats : scénarios fictifs, couverture partielle, absence d'intégrations natives et de validation réglementaire. Les références OWASP Agentic, MITRE ATLAS et ATT&CK, ainsi que NIST CSF, servent à situer les risques et les contrôles ; elles ne constituent pas une certification.

## 6. Livrables du hackathon

Le dernier résumé de Nila proposait quatre pièces à préparer pour la remise de dimanche midi :

1. Un dépôt lisible et un README expliquant le problème, l'architecture, le lancement, les tests et les limites.
2. Une vidéo de démonstration de deux à trois minutes, enregistrée sur le même parcours que la démo live.
3. Un deck d'environ huit slides pour un pitch de cinq minutes : problème, angle salariés/agents, solution, moteur commun, démo, déploiement visé, marché et équipe.
4. Une fiche de défense d'une page : scénario d'attaque, contrôle humain, références, métriques réellement mesurées et limites.

La démo live doit être faisable depuis une commande, aboutir à la console et fonctionner sans improviser des données. Le dépôt ne doit contenir que l'entreprise et les données fictives du scénario. Un scan de secrets visible dans le dépôt a été proposé ; ne montrer un badge que si le contrôle existe et passe réellement.

## 7. Priorités et décisions encore ouvertes

Le dernier résumé de Nila proposait cet ordre. Il ne contenait pas de validation point par point de Guilhem :

| Priorité proposée | Travail | État de décision dans Nila |
| --- | --- | --- |
| 1 | Démo live d'agent attaqué puis défendu et quatre livrables de remise | Proposé, cohérent avec la direction retenue |
| 2 | Scan de secrets avant commit et preuve visible | Proposé, à valider |
| 3 | Scènes « fausse facture/virement » et « MFA approuvé » | Proposées, seulement si le temps le permet |

Les conditions de sortie de la démo sont : parcours salarié et agent reliés à la vraie console ; décisions observables et persistantes ; export fidèle aux faits ; lancement documenté ; vidéo, deck et fiche alignés sur ce que le code fait. La console ne doit pas afficher une action de coupure pour un humain. Une tentative d'exfiltration ne doit pas devenir une exfiltration affirmée dans les textes.

## 8. Après le hackathon

La prochaine étape produit serait de remplacer les scènes simulées par des intégrations autorisées : poste, messagerie, navigateur et agents réellement déployés, avec installation et exploitation sur site. Elle demanderait aussi une gestion des identités et des droits, une politique de rétention, une mesure sur des jeux indépendants et des essais avec des analystes SOC.

Les leurres externes, le physique, les appels, les chatbots publics, la communication entre agents et la mémoire persistante restent des pistes à instruire séparément. Ils ne sont ni requis pour la démo ni annoncés comme livrés.

## 9. Cible commerciale et travail partagé

L'hypothèse de client est une organisation qui cumule beaucoup de salariés, des données sensibles et des agents IA déjà utilisés ou en cours de déploiement. Fintech, santé, SaaS et marketplaces sont des terrains de recherche. Les noms évoqués pendant la session, Revolut, Qonto, Doctolib, Alan et Back Market, sont des **prospects à vérifier**, pas des clients ni des preuves d'adoption d'agents. Le prix de 5 à 30 € par utilisateur et par mois évoqué dans le pitch est une hypothèse non testée.

Le premier partage de travail donnait à Guilhem les capteurs, la passerelle, la boîte noire et le banc ; à Paul le scénario fictif, le deck, la fiche de défense, le modèle économique et la vidéo. Ce partage date du cadrage initial. Depuis, Guilhem a demandé qu'une tâche de code isolée du banc de mesure soit préparée pour Paul, sur une branche et avec une PR, sans modifier les parcours de démo en parallèle.

La règle pour toute communication externe est simple : montrer ce qui tourne, distinguer la cible du prototype, et ne publier ni données personnelles, ni secrets, ni chiffres de performance non mesurés.

## 10. Direction de la page et des visuels

Le brief design rédigé ensuite dans la session fixe une page pour deux lecteurs : l'équipe SOC, qui veut voir la preuve et la décision, et le décideur, qui veut comprendre le risque et le déploiement. La page doit mener du mail de phishing à l'agent détourné, puis à leur console commune. Les captures du produit et les visuels déjà présents dans `landing/img/` servent de matière ; un schéma doit rester présenté comme un schéma et non comme une intégration réelle.

La direction choisie est un fond bleu nuit, des panneaux de verre discrets et une typographie Space Grotesk pour les titres, IBM Plex Mono pour les données. Le cyan signale le parcours salarié, le bleu-violet celui des agents ; l'ambre est réservé à la piste physique. Éviter les néons saturés, les codes de jeu vidéo et les animations décoratives. Vérifier la lisibilité à 1440 et 390 px, sans débordement horizontal.

L'ordre de lecture proposé est : promesse et visuel, problème du phishing et des agents, moteur commun, gestes salarié, agent attaqué puis défendu, console et preuves, limites et déploiement visé, références, accès à la démo. Les chiffres ne figurent sur la page qu'avec leur source et leur périmètre. Le taux de 33,1 % vient du benchmark KnowBe4 ; les métriques du prototype demandent une campagne de mesure reproductible avant publication.
